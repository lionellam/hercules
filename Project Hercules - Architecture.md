## 1. Purpose

Record the architecture of the Project Hercules web app (Phase 2 — Web App v1) and the decisions behind it, so the reasons remain clear as the project evolves. Each decision lists the option chosen and the main reason; superseded decisions should be struck through rather than deleted.

## 2. System Overview

```
 ┌──────────────────────────┐
 │  Phone (PWA, Safari)     │
 │  Log · History ·         │
 │  Summary · Settings      │
 └────────────┬─────────────┘
              │ HTTPS
 ┌────────────▼─────────────┐        ┌──────────────────────────┐
 │  Next.js app on Vercel   │───────▶│  Google sign-in          │
 │  (TypeScript)            │        │  (allow-list checked     │
 │  - pages / UI            │        │   by the app)            │
 │  - API routes            │        └──────────────────────────┘
 │  - allow-list & limits   │
 │                          │        ┌──────────────────────────┐
 │                          │───────▶│  Anthropic API           │
 │                          │        │  Claude Haiku 5.5        │
 │                          │        │  (parse only)            │
 │                          │        └──────────────────────────┘
 │                          │
 │                          │        ┌──────────────────────────┐
 │                          │───────▶│  Neon (Postgres)         │
 └──────────────────────────┘        │  users · categories ·    │
                                     │  expenses ·              │
                                     │  allowed_emails ·        │
                                     │  parse_events            │
                                     └──────────────────────────┘

 Separate, local only:  Python CLI → Phi-4 via Ollama → SQLite
```

For the step-by-step view of logging an expense (who does each step, every request to the database and to Claude, and where the flow can stop), see the [Expense Flow](Project%20Hercules%20-%20Expense%20Flow.html) swimlane diagram, also published as [flow.html](https://lionellam.github.io/hercules/flow.html).

The language model is called only to parse a single expense into structured fields. All other logic — sign-in checks, validation, storage, retrieval, edits, and usage limits — is deterministic application code, in line with the Specification's AI boundary.

## 3. Decision Record

### 3.1 Users and access

| # | Decision | Reason |
|---|---|---|
| 1 | **Users:** family members and close friends only | The app meets a personal and family need; it is not a public product |
| 2 | **Allow-list** of invited email addresses | Keeps access limited to known people even though anyone can attempt Google sign-in |
| 3 | **Google sign-in only** | Free, familiar, and works on both iPhone and Android. Sign in with Apple was considered but requires a paid Apple Developer Program membership (US$99/year) |

### 3.2 Language model and privacy

| # | Decision | Reason |
|---|---|---|
| 4 | **Expense text may be sent to a cloud model provider**, using a provider whose API data is not used for training | Enables a hosted app without running inference at home. Accepted trade-off against the earlier local-only privacy stance. *Updated 20 November 2026 (1.5.0):* with the experimental Intelligent Merchant Selection switched on, the merchant names from the current month's expenses are sent with each entry too (decision 40) |
| 5 | **Anthropic, Claude Haiku 5.5** (`claude-haiku-5-5`), with structured outputs | Fast and inexpensive (US$0.10 / US$0.50 per million input/output tokens); simple extraction is well within its abilities; structured outputs guarantee valid JSON, removing parse failures seen with the local model. Swapping models later is a configuration change. Gemini's free tier was considered (26 Oct 2026) but not chosen: its terms allow free-tier inputs to be used to improve Google's products, conflicting with decision 4, while Haiku's expected cost is only around US$0.10/month |
| 6 | **Cloud model only** for the web app | A cloud-hosted app cannot reach Ollama on a home machine. The parser code is kept tidy enough to add another backend later |
| 7 | **Cost guards:** US$5/month spend limit on the Anthropic account; 100 parses per user per day in the app | Normal use costs cents per month; the limits protect against bugs or misuse |

### 3.3 Hosting and data

| # | Decision | Reason |
|---|---|---|
| 8 | **Vercel** for hosting | Strong fit for a TypeScript / Next.js app; free Hobby plan suits a personal, non-commercial family app (terms confirmed 2 November 2026: Hobby plan active, no payment method on file) |
| 9 | **Free Vercel address** (`*.vercel.app`) for now | No cost; Google sign-in works with it; a custom domain can be added later without code changes |
| 10 | **Neon** (hosted Postgres) | SQLite cannot persist on Vercel. Neon is plain Postgres designed for serverless hosts, available through Vercel's marketplace with a free tier |
| 11 | **One-off import** of existing CLI data into the owner's account | Keeps the full spending history (July 2026 onwards) in one place from day one |
| 12 | **CLI stays separate** — local SQLite and Phi-4, unchanged | Remains a lightweight, offline, experimental tool (e.g. for trying prompt changes). The web app is the main record; entries logged in the CLI after the import are not synced |
| 22 | **Server runs in Vercel's Singapore region** (`sin1`, set in `web/vercel.json`) | Puts the server next to the Neon database (`ap-southeast-1`) and the app's users. Vercel's default (`iad1`, US East) sent each signed-in request across the Pacific and back, plus again for each database lookup |

| 40 | **Intelligent Merchant Selection (experimental, 1.5.0):** when the switch is on, the Log screen's parse request says so (`knownMerchants: true`). The list is added to the prompt with the rule: return the name exactly as listed when the text clearly refers to it, even shortened, in different capitals or only in part; otherwise return the merchant as written, or null. The owner found that "Groceries from Sheng Siong at $7" came back with no merchant. Checks against the language model showed the earlier rule dropped new merchants more often as the list grew: with 50 known merchants, Sheng Siong was dropped in all 10 runs, while known names still matched. With the new rule, new merchants were kept in every run with 20 and 50 known merchants, known names still matched, and a new merchant typed untidily ("dintaifung") is tidied as with the switch off ("Din Tai Fung"). Returning a new merchant exactly as typed was tried and set aside by the owner, as it lost that tidying. Only the text added when the switch is on changed: with the switch off, the prompt is identical, character for character. The owner asked for it, so the list isn't empty early in a month (on 1 December, November's merchants still match). A rolling 60 days was considered and set aside: the app thinks in calendar months elsewhere (Summary shows this month and last). Ranking this month's names before last month's was also set aside, for the simpler most-used rule. Trade-offs: up to two months of merchant names go to the model (still at most 50), and a longer list gives more chances for the known gap below (a business sharing a word with a listed merchant). With the switch off, the prompt is unchanged. | The owner asked for parsing to learn the month's merchant names, so variants such as "ntuc" or "fairprice" come back as "NTUC FairPrice" and History, search and the CSV stay consistent. Giving the model the list was chosen over matching in code, because the model can recognise abbreviations and partial names that simple text matching would miss, without a separate table of aliases. Grouping by capitals and spaces (chosen by the owner over a plain distinct) stops a badly typed name being offered back as a valid choice. The cap of 50 keeps the prompt small and the parse fast; a typical month has far fewer. Only the current month is used, by the owner's choice, so the list follows recent habits and stays short; early in a month there may be nothing to match. Trade-off: while on, this month's merchant names are sent to the model with each entry (decision 4). No visible change on the review sheet was chosen by the owner over a note saying a name was matched |
| 41 | **Security headers and dependency updates (1.5.1):** every page and API response carries `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` (the app can't be shown inside another site's frame), `X-Content-Type-Options: nosniff` and `Referrer-Policy: same-origin`, set in `web/next.config.ts`; Vercel already adds HSTS. Next.js is pinned at 16.4.6 (with `eslint-config-next` to match), up from 16.4.3 | From a security review on 20 November 2026, which found access checks, query parameters, input checks, CSV formula guarding and secrets handling sound. Without a frame rule, another site could show Hercules in a frame and trick a signed-in person into tapping something (clickjacking). A full Content-Security-Policy was considered and left for now: the inline theme script and the framework's own scripts would need nonces or hashes, for little gain in an app that shows no other people's content. Next.js 16.4.3 had a moderate advisory (seven issues); most involve features Hercules doesn't use, and the one touching Cache Components concerns pages with URL parameters, which Hercules's pages don't have, but the patch release was cheap to take. Two lower-priority findings were set aside by the owner: the daily parse limit's count and record are two steps, so simultaneous requests could slightly exceed it (the US$5 spend cap still applies), and Google sign-in doesn't check `email_verified` |
| 42 | **Vercel builds only when the app changes (1.5.5):** `web/vercel.json` sets an ignored build step, `git diff --quiet ${VERCEL_GIT_PREVIOUS_SHA:-HEAD^} HEAD -- .`, run in `web/`. It compares what's being pushed with the last successful deploy (or, if Vercel doesn't give one, the previous commit): if nothing under `web/` changed, the build is skipped and the running deploy stays; if anything did, or the comparison can't be made, the app builds as before | Settings shows when the running version was built (decision 34), and Vercel was rebuilding on every push to `main`, documents included. On 22 November 2026 the owner noticed that "Last updated" and the commit code moved with each GitHub Pages push, while the changelog's newest version, 1.5.4, was dated the day before. Skipping documents-only builds (chosen by the owner) keeps the date and code pointing at a real app change, and stops builds that change nothing. Showing the release date instead, and leaving it as it was, were set aside. Comparing with the last successful deploy, not just the previous commit, means a push of several commits still builds if any of them changed the app. If the comparison fails (for example, an old commit missing from Vercel's copy), it builds, so an app change is never skipped |
